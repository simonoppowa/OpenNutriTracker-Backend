# opennutritracker-backend

Supabase backend for [OpenNutriTracker](https://github.com/simonoppowa/OpenNutriTracker):
a multi-source food reference database (~27.7k foods by default,
optionally ~2M with FDC branded) served through a single canonical
schema and one app-facing materialized view.

Each national food database is downloaded, converted to a common set of
CSVs, and bulk-loaded into shared tables. The Flutter app reads only the
`food_summary` materialized view (24 per-100g nutrients matching
`MealNutrimentsDBO`, default serving, image URLs, tags) plus
`food_translation` for i18n.

This repo contains **code only**. Raw downloads and converted CSVs are
gitignored — they are large and regenerated by the scripts. All sources
above permit reuse; attribute each per the table when serving the data.

## Setup

```bash
python3 -m pip install psycopg2-binary openpyxl requests

export SUPABASE_DB_URL='postgresql://postgres.<ref>:<password>@aws-0-<region>.pooler.supabase.com:5432/postgres'
# use the SESSION pooler (port 5432); the transaction pooler (6543) cannot COPY.
# passwords with special chars are percent-encoded automatically by the scripts.
```

## Quick start (one command)

`run_pipeline.py` orchestrates download → convert → create schema →
import for the sources and steps you choose:

```bash
cd scripts
python3 run_pipeline.py --source fdc bls --action all --db "$SUPABASE_DB_URL"
```

It writes raw data to `./source`, converted CSVs to `./out/<source>`,
creates the schema, then imports (FDC first, then BLS appended). Flags:
`--branded` (add the ~2M FDC branded set), `--work-dir`, `--dry-run`.
The default is `--source fdc bls`; `ciqual`, `fineli`, `frida`, `mvt` and
`slv` are opt-in (name them in `--source`).

## Manual pipeline (step by step)

```bash
# 0. Create the schema once (tables, view, RLS, indexes, storage bucket):
psql "$SUPABASE_DB_URL" -f sql/schema.sql

cd scripts

# 1. FDC — download (foundation + sr_legacy + fndds), convert, import.
#    Add 'branded' only if NOT on the Supabase free tier (~2M foods).
python3 fdc/download_fdc.py --output source
python3 fdc/fdc_to_ont_csv.py --output out/fdc        # reads ./source
python3 shared/import_fdc.py --csv-dir out/fdc

# 2. BLS (CC BY 4.0) — download, convert, import (append).
python3 bls/download_bls.py --output source            # -> source/bls
python3 bls/bls_to_ont_csv.py --output out/bls         # reads source/bls
python3 shared/import_fdc.py --csv-dir out/bls --append

# 3. INDB / TBCA (data supplied manually — see each script's --help).
python3 indb/indb_to_ont_csv.py --data Anuvaad_INDB_2024.11.xlsx --output out/indb
python3 shared/import_fdc.py --csv-dir out/indb --append
python3 tbca/tbca_to_ont_csv.py --foods tbca_foods.csv \
    --nutrients tbca_nutrients_wide.csv --output out/tbca
python3 shared/import_fdc.py --csv-dir out/tbca --append

# 3b. CIQUAL (France, Licence Ouverte) — download, convert, import (append).
python3 ciqual/download_ciqual.py --output source      # -> source/ciqual
python3 ciqual/ciqual_to_ont_csv.py --output out/ciqual # reads source/ciqual
python3 shared/import_fdc.py --csv-dir out/ciqual --append

# 3c. Fineli (CC BY 4.0, THL) — download, convert, import (append).
#     fineli.fi may answer scripts with a bot-protection challenge; then
#     save "basic package 2" from https://fineli.fi/fineli/en/avoin-data in
#     a browser and pass it with --zip.
python3 fineli/download_fineli.py --output source      # -> source/fineli
python3 fineli/download_fineli.py --zip ~/Downloads/<package>.zip  # fallback
python3 fineli/fineli_to_ont_csv.py --output out/fineli  # reads source/fineli
python3 shared/import_fdc.py --csv-dir out/fineli --append

# 3d. Frida / Danish FCDB (CC BY 4.0) — download, convert, import (append).
python3 frida/download_frida.py --output source        # -> source/frida
python3 frida/frida_to_ont_csv.py --output out/frida   # reads source/frida
python3 shared/import_fdc.py --csv-dir out/frida --append

# 3e. Matvaretabellen (CC BY 4.0) — JSON API, English + Norwegian names.
python3 mvt/download_mvt.py --output source            # -> source/mvt
python3 mvt/mvt_to_ont_csv.py --output out/mvt         # reads source/mvt
python3 shared/import_fdc.py --csv-dir out/mvt --append

# 3f. SLV / Livsmedelsverket (CC BY 4.0) — page the open API (resumable,
#     ~5k polite requests), convert, import (append).
python3 slv/download_slv.py --output source            # -> source/slv
python3 slv/slv_to_ont_csv.py --output out/slv         # reads source/slv
python3 shared/import_fdc.py --csv-dir out/slv --append

# 4. (optional) machine-translate every source's names into a language.
#    Reads the DB, writes out/<source>/food_translation_de.csv, then asks
#    whether to write the rows back into food_translation.
export DEEPL_API_KEY="your-key:fx"
python3 shared/translate_all.py --target de
```

`import_fdc.py` refreshes `food_summary` at the end of every run.

To ship the same data without Supabase, build the offline SQLite file
straight from the converted CSVs (no Postgres involved) — see
[Offline SQLite database](#offline-sqlite-database):

```bash
python3 shared/build_sqlite.py \
    --csv-dir out/fdc out/bls out/ciqual out/fineli out/frida out/mvt out/slv \
    --output out/sqlite/foods.sqlite
python3 shared/build_sqlite.py --check out/sqlite/foods.sqlite
```

## Scripts

### Orchestration
- **`run_pipeline.py`** — runs the whole flow (download/convert/schema/
  import) for any mix of sources and actions. FDC is always imported
  before BLS (BLS reuses FDC's shared `nutrient` table); the first import
  truncates, the rest append. `--dry-run` prints the commands only.

### Downloaders (raw data → `./source`)
- **`fdc/download_fdc.py`** — scrapes the FDC download page for the newest
  CSV zip of each dataset (foundation, sr_legacy, fndds; `branded` opt-in)
  and extracts them into `source/<dataset>/`. Handles the date-versioned
  URLs automatically.
- **`bls/download_bls.py`** — downloads the BLS 4.0 zip from blsdb.de
  (handles its session-token gating) into `source/bls/`. If auto-detect
  fails, pass the link from the browser via `--url`.
- **`ciqual/download_ciqual.py`** — finds the newest CIQUAL release on
  recherche.data.gouv.fr (Dataverse API; ANSES moved it there in 2025)
  and downloads its XML tables + PDF docs into `source/ciqual/`. `--doi`
  pins a release; `--url` takes a zip of the XML files instead.
- **`fineli/download_fineli.py`** — reads the Fineli open-data page, tries
  every package zip and keeps the one with the most components (basic
  package 2) into `source/fineli/`. If fineli.fi refuses the scripted
  request it says so; save the zip in a browser and pass `--zip`.
- **`frida/download_frida.py`** — finds the newest Danish Food Composition
  Database release on DTU Data via the Figshare API, downloads its
  `FCDB_*_Dataset.xlsx` into `source/frida/` and checks the MD5. No session
  gating; `--article`/`--url` pin a release, `--docs` adds the English PDF.
- **`mvt/download_mvt.py`** — fetches the Matvaretabellen JSON exports
  (foods, food groups, nutrients, sources; English + Norwegian Bokmål)
  from matvaretabellen.no/api into `source/mvt/`. Standard library only.
- **`slv/download_slv.py`** — pages through the Livsmedelsverket open API
  (no bulk file exists) and caches the raw JSON in `source/slv/`: food
  lists in English and Swedish plus per-food nutrient values and
  classifications. Sequential with a small delay; resumable (`--refresh`
  re-fetches).

### Converters (raw source → Supabase CSVs)
Each turns one source into the shared CSV set (`food`, `food_nutrient`,
`food_portion`, `food_translation`, ...) matching `sql/schema.sql`.
All map to the 24 canonical nutrients and normalize units at import.
- **`fdc/fdc_to_ont_csv.py`** — FDC Foundation / SR Legacy / FNDDS /
  Branded. Accepts extracted dirs, official zips, or `--source-dir`
  (defaults to `./source`). Handles the FNDDS legacy nutrient-number
  quirk and streams the huge branded files.
- **`bls/bls_to_ont_csv.py`** — BLS 4.0 xlsx. German names become native
  `food_translation` (`de`); unit factors applied (e.g. B6 µg→mg).
  Auto-finds the xlsx under `./source/bls`.
- **`indb/indb_to_ont_csv.py`** — Anuvaad INDB xlsx. Serving sizes and
  romanized aliases extracted; fat unit conversions applied.
- **`tbca/tbca_to_ont_csv.py`** — scraped TBCA CSVs. Groups → categories,
  scientific names → aliases.
- **`ciqual/ciqual_to_ont_csv.py`** — CIQUAL XML. English names in
  `food`, French names as native `food_translation` (`fr`), sub-groups →
  categories, scientific names → aliases. `traces` / `< x` (below the
  quantification limit) become 0 with `max = x`; `-` stays NULL.
- **`fineli/fineli_to_ont_csv.py`** — Fineli CSV package. English names
  in `food`, Finnish/Swedish as native `food_translation` (`fi`, `sv`);
  food-use classes → categories; household portions (pieces, portions,
  dl, tbsp, tsp) → `food_portion`; energy kJ → kcal (÷4.184). Covers all
  24 canonical nutrients, trans fat included.
- **`frida/frida_to_ont_csv.py`** — Danish FCDB (Frida) xlsx. English
  names in `food`, Danish as native `food_translation` (`da`); leaf food
  groups → categories; vitamin A derived as µg RAE from Frida's RE /
  retinol / β-carotene. Auto-finds the xlsx under `./source/frida`.
- **`mvt/mvt_to_ont_csv.py`** — Matvaretabellen JSON. English names in
  `food`, Bokmål names as native `food_translation` (`nb`), food groups →
  categories, household measures → `food_portion` (all 24 nutrients
  already canonical; kcal published directly, vitamin A in µg RAE).
- **`slv/slv_to_ont_csv.py`** — cached Livsmedelsverket JSON. English names
  in `food`, Swedish names as native `food_translation` (`sv`), "Main
  group" → categories. Energy from the kcal row; `VITA` is already RAE.

### Loading & utilities (`shared/`)
- **`shared/import_fdc.py`** — psycopg2 bulk loader for any converted CSV
  dir. Truncates by default, `--append` for additional sources; derives
  COPY column lists from CSV headers; refreshes `food_summary`; works for
  every source, not just FDC.
- **`shared/translate_all.py`** — universal DeepL translator. Reads the DB
  for every source's untranslated English descriptions, writes each
  source's rows to `out/<source>/food_translation_<locale>.csv`, then
  prompts whether to insert them into `food_translation` (`ON CONFLICT DO
  NOTHING`). Resumable; skips foods that already have a translation (e.g.
  BLS German for `de`). Reads `$DEEPL_API_KEY` / `$SUPABASE_DB_URL`.

- **`shared/review_translations.py`** — takes one locale's machine
  translations to `source='verified'` via a CSV a native speaker can edit
  without touching SQL. Two vocabularies:

  - `--target portions` — `food_portion_translation.portion_description`
    (`1 cup`, `1 slice`). **This is the one that matters**: it is what a user
    reads, and `food_summary.serving_size` is built from it.
  - `--target units` — `measure_unit_translation.name` (`cup`, `slice`).
    Reaches only 0.5% of portions, because `measure_unit` is `undetermined`
    for 36,495 of 36,682 rows.

  `--export` writes `review/<target>_<locale>.csv` (English string, current
  translation, a blank `corrected` column, and a note on the ambiguous ones);
  `--apply` applies corrections and promotes the locale. `-` in `corrected`
  deletes the row, so an entry with no good word falls back rather than
  showing a bad guess. `--dry-run` prints the plan and writes nothing.

  Distinct strings only: `1 cup` is 3,056 portion rows and appears once.

  **Promotion is per locale and all-or-nothing.** `verified` claims somebody
  read the list, so `--apply` refuses a CSV that has lost rows and names what
  is missing — otherwise a half-finished pass and a finished one are
  indistinguishable afterwards. `ai_generated` stays `true` after promotion:
  it records where the text came from, not whether it is trusted.

### Offline database (`shared/build_sqlite.py`)
- **`shared/build_sqlite.py`** — builds `foods.sqlite` (+ `foods.sqlite.gz`
  and `ATTRIBUTION.md`) from converted CSV folders, for the app to query on
  the phone. Standard library only; Python 3.12+. See
  [Offline SQLite database](#offline-sqlite-database).

### Testing
- **`shared/test_build_sqlite.py`** — builds a database from the fixture
  CSVs in `shared/testdata/sqlite` and checks all five RPCs, the
  `food_summary` derivations and the review guard. No database needed:
  `python3 scripts/shared/test_build_sqlite.py`.
- **`shared/test_review_translations.py`** — exercises that completeness
  guard on its own, without a database. Run it directly:
  `python3 scripts/shared/test_review_translations.py`.
- **`test_against_source.py`** — samples random foods from Supabase (or a
  converted CSV dir with `--csv-dir`) and validates each against the raw
  source files: description, short_title, all 24 nutrients (re-derived via
  each source's mapping + unit factors), and the native names: BLS German,
  CIQUAL French, Fineli Finnish/Swedish, Frida Danish, Matvaretabellen
  Norwegian, SLV Swedish. Exit 1 on any mismatch; `-v` logs every check.

```bash
cd scripts
python3 test_against_source.py --source-dir source --samples 50   # vs Supabase
python3 test_against_source.py --csv-dir out/ciqual --source ciqual # CIQUAL CSVs, offline
python3 test_against_source.py --csv-dir out/fineli --source fineli  # offline
python3 test_against_source.py --csv-dir out/frida --source frida    # offline
python3 test_against_source.py --csv-dir out/mvt --source-dir source --source mvt  # offline
python3 test_against_source.py --csv-dir out/slv --source-dir source --source slv  # offline
```

## Offline SQLite database

`scripts/shared/build_sqlite.py` turns the converted CSV folders into one
SQLite file that answers the app's five RPCs — `search_food_summary`,
`search_food_translation`, `food_summary_by_ids`,
`portion_labels_by_food_ids`, `portions_by_food_ids` — with the same rows
and row shapes the Supabase functions return (their final definitions in
`schema.sql`, `label_en` and the title-first order included). The app
downloads `foods.sqlite.gz` from this repo's releases and queries it
locally.

```bash
cd scripts
python3 shared/build_sqlite.py --csv-dir out/fdc out/bls out/ciqual \
    out/fineli out/frida out/mvt out/slv --output out/sqlite/foods.sqlite
python3 shared/build_sqlite.py --check out/sqlite/foods.sqlite
python3 shared/test_build_sqlite.py
```

- **What it holds.** `food_summary` (the materialized view, every column and
  derivation: the 24 pivoted nutrients, the default serving from the first
  portion, `serving_unit` 'undetermined' → 'portion', the "<amount>
  <modifier>" fallback, `has_portion`), `food_translation`, the deliverable
  portions numbered as `portions_by_food_ids` numbers them, the two
  `*_translation_seed.sql` migrations (keyed by the English text they join
  on), `food_source` with `license_note`, and `meta` (`schema_version`,
  `build_date`, `food_count`, per-source and per-locale counts). FTS5
  indexes: `porter unicode61` on `food_summary.name`, `unicode61
  remove_diacritics 2` on translations, both with `tokenchars '/'`.
- **Numbers** keep the JSON type PostgREST gives them: a value whose CSV
  text has no decimal point is an integer, anything else a real.
- **Size.** `VACUUM` at the page size that gives the smallest file
  (`--page-size auto`; 8192 for the full build), no free pages, FTS
  segments merged. Full build (FDC Foundation/SR Legacy/Survey, BLS and the
  five European sources, 34,673 foods): ~16 MB, ~4.6 MB gzipped.
- **Reviewed translations.** The seeds are machine output, which the RPCs
  never show. `--review review/portions_de.csv` takes a CSV from
  `review_translations.py --export` after review and promotes that locale
  to 'verified' exactly as `--apply` does, completeness guard included.
- **Machine food names** from `translate_all.py`
  (`out/<source>/food_translation_<locale>.csv`) are loaded when present,
  after the native ones, "on conflict do nothing".
- **Checked against Postgres.** The full build was loaded into Postgres 17
  with `schema.sql`, the seeds and CSV `COPY`: all 34,673 `food_summary`
  rows and all 25,217 translations are identical (values and JSON types),
  and 391 of 409 sample RPC calls returned identical rows in identical
  order. The other 18 are the differences below.
- **Bump `SCHEMA_VERSION`** whenever the file's tables or columns change:
  the app refuses a file whose `meta.schema_version` it does not know.

### Where the offline search differs from Postgres

Match sets can differ; the order of whatever matches does not (`has_portion
desc`, title = term, `length(name)`, `food_id`, computed from the same
values). Postgres's text search cannot be loaded into SQLite, so:

1. **Stemmer.** FTS5's `porter` is the original Porter algorithm; Postgres's
   `english` uses Snowball English (Porter2). They mostly agree, but not
   always: `pies` stems to `pi` in Porter and `pie` in Snowball, so `pie`
   misses "pies"; `fried` → `fri` matches neither "fry" nor "frying" in
   Porter.
2. **Stopwords.** FTS5 has none; the query drops Postgres's `english.stop`
   words instead. Inside a quoted phrase only leading and trailing
   stopwords are dropped, and inner ones must be present and adjacent,
   where Postgres only keeps their position gap.
3. **Diacritics.** FTS5 folds them (`remove_diacritics 1` for English,
   `2` for translations); Postgres's `english` and `simple` do not. Offline,
   `cafe` finds "café", `apple` finds Swedish "äpple" and `Äpfel` finds
   "Apfel" — Postgres finds none of those.
4. **Hyphens.** Postgres indexes "low-fat" as `low-fat`, `low` and `fat`,
   and a hyphenated query word must match the compound; FTS5 splits at the
   hyphen and matches the parts as a phrase, so `low-fat` also finds
   "low fat".
5. **Numbers and dots.** Postgres keeps `2.5` and `foo.bar` as one token;
   FTS5 splits at the dot, so `2` matches "2.5 % fat".
6. **Slashes.** Postgres reads `mango/papaya` as one file-path token; the
   `tokenchars '/'` option does the same. Postgres's file-path rule is
   ASCII-only, though, so it splits "mælk/fløde" before the `æ` and finds
   it for `mælk`; FTS5 keeps it whole and does not.
7. **Negation only.** `-cheese` alone matches every food without cheese in
   Postgres; FTS5 has no unary NOT, so such a term (or `or` branch) matches
   nothing.
8. **Case and trim.** `lower()`/`btrim()` for the title comparison are
   applied by Python at build time and by Dart at query time instead of by
   Postgres; they agree except for locale-specific case rules (e.g. Turkish
   dotted I).
9. **Duplicate ids.** Postgres's `unnest` returns a row per repeated id in
   `portions_by_food_ids`/`portion_labels_by_food_ids`; the offline version
   returns each food once (`portion_labels` keeps repeats and the id order).

## SQL (`sql/`)
- **`schema.sql`** — full DDL: tables, indexes (pg_trgm + FTS + tag/
  barcode), RLS (public read, service_role writes), the `food_summary`
  materialized view, and the `food-images` storage bucket.
- **`import_fdc.sql`**, **`import_bls.sql`** — psql `\copy` alternatives
  to `import_fdc.py` (client-side; run with `psql`, not the dashboard).

vocabulary, i18n rules) live in the script docstrings and
`diagrams/multisource_food_schema.mermaid`. Keep the diagram,
`sql/schema.sql`, and the converters in sync when changing the schema.
